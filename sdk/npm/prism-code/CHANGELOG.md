- A draft form of `prism/spec/1`, so a model only translates (#666, experimental). A draft holds what the user said: a `title`, the `fields`, the `rules` and the `otherwise` answer, and leaves out any of `purpose`, `outcomes`, `properties` and `examples`. `completeSpec` (`src/journey/complete.mjs`, pure: no clock, no randomness, no I/O) turns it into an ordinary whole spec, the same bytes from the same draft: the answers the rules give, in first-appearance order; a purpose from the answers and the fields and a name from the title; the first request each rule decides and one for `otherwise` as examples, at most six; and, when the draft has fewer than three guarantees, proposals read off the rules, up to three in all, each kept only when no request breaks it and each with a `why` that starts "Proposed by Prism". A spec that holds all four members is not a draft: it comes back as before and nothing is proposed again, so a struck guarantee stays struck. It is still `prism/spec/1`; there is no new schema version.
- `prism_spec` takes a draft and completes it, returning `proposed` (the ids of proposed guarantees) and `notes`; a draft written to `prism/spec.json` is completed when Prism next reads it. The review lists proposed guarantees first, marked as proposed. The `prism_spec` input no longer requires `purpose` and `outcomes`. The MCP instructions and the skill tell a model to write only what the user said, compactly, and a guarantee only when the user stated one.
- A number field compared with a bare word that names another number field (`"value": "limit"`) is read as that field (`{"field": "limit"}`) when a spec is passed to `prism_spec`, and named in `notes`: a number is never compared with text, so it has one meaning. Measured with Qwen3 30B, it was every refusal of a rules-only draft. Reading `spec.json` strictly still refuses it, now saying how to write it.
- Two clean-ups when a spec is passed to `prism_spec`, each named in `notes`: an `invalid` listed among the answers that no rule, `otherwise` or guarantee answers is dropped (it used to be refused as `outcomes.reserved`), and a guarantee whose conditions no request can meet is dropped, only when every candidate request was tried. The stored `spec.json` is the spec after the drops, and its address is the seal.
- `checkSpec` completes and checks a spec in one call, and `repairMessage` says what to tell its author: a guarantee the rules break is named as the JSON that was written, beside the rule that decides against it and the request that shows the conflict, with the two ways out; any other refusal is given in the checker's words. `prism_spec` returns it as `repair`.
- `DRAFT_JSON_SCHEMA` and `SPEC_JSON_SCHEMA` (`src/journey/spec-schema.mjs`): `prism/spec/1` as JSON Schema, the draft form and the whole spec, for a caller that can hold a model's answer to a schema. Both are closed, and number bounds are whole and not negative.
- `prism/spec/2`, the JSON spec of an app that keeps state between steps (#664, `docs/proposals/664-stateful-spec.md`, experimental). Bounded `state` with a start, `actions` with inputs and ordered rules whose `change` sets, adds to or subtracts from the state, an `otherwise` per action, properties over every reachable state, and examples as sessions. It is read as strictly as `prism/spec/1`, with its own registered refusals (`STATEFUL_REFUSALS`), renders to the same bytes from the same JSON, and carries the same seal, `[prism/spec/2 blake3:<hex>]`, so `prism-code check --spec` holds a stateful app to its JSON. Lean proves the bounds and each property by induction over a session's steps, every theorem `linear_arithmetic`. A session runs on the text profile as one request, its steps separated by `;`, answered with the last outcome and the state. `prism_spec` takes either schema; a model still writes only JSON. A stateful app builds on this machine only for now: the GitHub template is for decision apps.
- An unknown `schema` in a spec is refused as `spec.schema`, naming both schemas, rather than as an unknown member.

### Breaking Changes

- Every app carries a seal: the UOR content address of the `prism/spec.json` it was built from (`blake3:<hex>`, the kappa its canonical bytes hash to, the same name a holo labels its own blobs with). It rides in the model's description, so it is inside the holo's model blob, whose label is that blob's content address and whose bytes the footer covers; changing the seal changes the holo and the integrity check refuses it. `prism-code check <holo> --spec <file>` holds an app to a spec and fails when it was built from another, or carries no seal; with no flag, a `spec.json` beside the holo is reported. A build whose holo seals another spec is refused.
- `prism/spec.json` is the one input of every Prism app, and the model is rendered from it alone. An agent writes or edits that JSON; Prism reads it strictly, keeps it as canonical JSON (RFC 8785) and records its SHA-256 as `specHash`. The same JSON always gives the same LexLean, byte for byte, whatever the clock, time zone, locale or working directory.
- Reading a spec refuses what it used to accept: a member `prism/spec/1` does not define (`json.member`), a duplicate key (`json.duplicate`), a number that is not a whole number within plus or minus 2^53 (`json.number`), and text that is not JSON (`json.syntax`), each naming its JSON path. `prism_spec` holds an agent's spec to the same rules, so a tool call and a hand-edited file are refused alike.
- A model that is not what `prism/spec.json` renders to is refused at build, naming the files that differ. The model is generated, never edited.
- `prism_start` and `prism_spec` read `prism/spec.json` each call: an edit an agent made to that file directly becomes the spec, reported as a note. A `spec.json` that does not read blocks `prism_prove` and `prism_build` with its refusal, instead of building from a stale session.
- `spec.json` holds canonical bytes, not pretty-printed JSON. A tool that read the old formatting still parses it; nothing else changes.

- `setup` adds the hosted lexlean server (`https://mcp.uor.foundation/`) to agents only with `--hosted`. Without it, each agent gets the local Prism server and nothing else; an entry already there is left as it is.
- A proof may rest only on `propext`, `Quot.sound` and `Classical.choice`. The guided path used to record whatever axiom set Lean observed and prove again, so a proof resting on `sorryAx` or `Lean.ofReduceBool` (native_decide) passed; it is now refused, naming the declaration and the axiom.
- `init --sdk-image` relocks the template's LexLean project with the image's own compiler before `prismpm update`, so a template lock older than the image no longer fails with `LLC0102`. Every bind run has `--network none`. `prismpm update --toolchain` still reads the image's index from its registry, so binding is not yet fully offline.
- The build result says where Lean proved the model (this machine, the hosted verifier or the GitHub gate), and claims nothing when no proof of the model is recorded. Acceptance vectors are reported as tested, never as verified.

- One canonical path for every app. `build --unstable-author` and `check <holo> --unstable-author`, where an agent wrote the model, are removed; `build --unstable-author` now exits 64 with `unknown option --unstable-author`. An app comes from one `prism/spec/1` spec through the guided path.
- Nothing is sent to the hosted verifier unless asked. `verify --lean` and `build --check` run in the SDK image on this machine and use the hosted verifier only with `--hosted`; with no lockfile they exit 64 and name `--hosted`. The guided path proves locally unless `PRISM_CODE_TIER=hosted`, and builds locally unless the caller names a repository or `remote: github`.
- An integrity failure fails every policy, P0 included. `check` adds the reason `policy.integrity` and exits 1 for a damaged holo whatever the policy's minimum; `run-policy.json` with `minimum: P0` no longer passes one.
- The spec is never altered. Text that the model or its documents cannot carry as written is refused as `text.character`, `text.length` or `text.space`, naming the character, its code point and its JSON path, instead of being stripped, collapsed or cut.

- The developer view's glossary (#346, #347) renames two spellings of the command line, each kept as a deprecated alias through 0.8 that prints one warning naming the new term and is removed in 0.9.0:

  | Was | Now | Why |
  |---|---|---|
  | `prism-code history <app.holo>` | `prism-code record <app.holo>` | the developer view calls a history a recording, and `docker history` lists an image's layers |
  | `--holo <path>` (`replay`, `dev`) | `--image <path>` | the developer view calls a holo an image; `.holo` files keep their name |

  Verbs that `prism-code` hands to `prismpm` keep `prismpm`'s flags. Nothing below the developer surface changes: the `prism/history/1` schema, `Application.history()`, predicate URIs and error codes keep their names.
- `prism-code check` without a holo is removed (#584). It was the 0.2.0 spelling of `build --check`, announced as removed in 0.4.0, and still ran through 0.7.2 with a warning that named that version. It is now a usage error (exit 64) that names `prism-code build --check`. Migration: replace `prism-code check [args]` with `prism-code build --check [args]`.
- `load()` refuses an altered holo (#583). When the footer is not the BLAKE3 of the body, a content blob does not hash to its label, or the manifest, directory and provenance name different blobs, `load`, `loadArchive` and `fromFile` reject with `DigestMismatchError` (`code` `digest_mismatch`, `check` `holo.integrity`), and so does `loadClosure` when a closure file does not match its provenance. Before, the application opened and dispatched, and only `identities.verified` said otherwise. `{ allowUnverified: true }` opens it as before. `prism-code vectors` and `history` refuse it too; `--allow-unverified` replays it, and `vectors` then exits 1.
- `holo.verify()`, `holo.inspect()` and `prism-code check` give no verdict (`archive.table`) on any archive the Wire codec refuses (SPEC section 3), as the Rust verifier does: content blobs out of label order, an application manifest that is not the Wire template, a manifest reference that names no blob, a section kind or extension name out of place, or a row count other than eight (nine with the attestation row last). Such an archive used to get a failing verdict.

### Bugs Fixed
- A holo with one byte altered is refused as an integrity failure at load and at `run`, under every policy, before anything inside it is read. Before, a flip that left a text section invalid UTF-8 escaped as a raw `TypeError` (exit 70), and a flip inside a document or the manifest was named as that document's error. Every such refusal is now `digest_mismatch` with check `holo.integrity`, its message starts with `integrity failure:`, and `run` exits 1; only damage to the header or the section table, which locate the footer, is still refused structurally.

The verdict's reasons for a holo with no attestation section no longer cite closed issues #266, #267 and #284, and now read as the Rust verifier's do: "The holo carries no provenance statement." and the same for proof and replay.

- The static world-within-policy check (#283, `docs/proposals/283-world-within-policy.md`, experimental): the imports of the world a holo's contract names are compared with the granted capability set before the guest is compiled. `@prism-code/verify` reports a world that imports a capability kind the set grants none of as `world.capabilities` (`PP5602`, withholds P3, fails the default policy at every level), takes the grant as `policy.capabilities`, and exports `worldPolicy(contract, set)`. The runtime refuses such a holo at load with `CapabilityDeniedError` (`world.capabilities`) and reports `app.world` (`within`, `pure`, `effects`); `holo.experimental_verify()` judges the set the holo was loaded with. A world with no clock, random, socket, filesystem or unknown import is pure, and `inspect` prints `world.pure` and `world.effects`. `hologram:guest/core-wasm@1` imports nothing, so every existing holo is within its grant and pure.
- `prism-code init` and `npm create prism-code` (#281, experimental): scaffold a project from a template that is a byte-for-byte copy of a reviewed fixture (`text-request`, from `tests/fixtures/holo/ho-11-text-application`: a language-1.2 text application with its lexicon, Lean workspace and `lexlean.lock`) plus a generated `prism.toml` that grants nothing. `--sdk-image NAME@sha256:DIGEST` binds the project: it copies the image's `standards.lock` and writes `prismpm.lock` with `prismpm update --toolchain` in that image. No SDK release exists yet, so there is no default image. `create-prism-code` (new package, not yet published) runs the same code; `create-prism` on npm is an unrelated package. `scripts/sync-templates.mjs --check` keeps templates equal to their fixtures, and the manual `init end to end` workflow times `npm create prism-code` to `prism-code check` against the issue's two minutes.
- `prism-code check <holo> [--policy <file>] [--json]` (#270, experimental): judges a holo against a policy and prints its `prism/verdict/1` with the level, the policy result and every reason (each named by its title, such as `ProofMismatch`); exits 0 when the policy passes, 1 when it fails and 2 when no verdict was reached (not a holo, an unreadable policy, an unknown format revision), and with `--json` prints exactly one canonical verdict on 0 and 1 and nothing on 2. The policy file holds `name`, `minimum`, `digests` and `world` and is never read from the holo. A holo that carries an attestation section exits 2 until #267's wire model change adds the format revision that admits it. From P2 up the text form prints what the check trusts the signer for. `@prism-code/verify` gains the eight `prism/proof/v1` statement checks (`src/statements.mjs`, PP5501 to PP5507), which `verify` joins when that revision lands.
- `prism-code build --check` runs `prismpm check` in the SDK image: it validates the model and writes nothing.
- CLI plugins in `prism-code` (#293, experimental): an executable `prism-<name>` on the PATH runs as `prism-code <name>` (and as `prism <name>` after the rename), with arguments and exit code passed through; built-in verbs always win, the first PATH directory wins, and Windows resolves by `PATHEXT` and quotes `.cmd` arguments so npm shims work. A plugin describes itself with `prism-cli-plugin-metadata` and is listed under its own Plugins heading in `--help`, or as invalid and never run. Error hooks, after Docker's `error-hooks` (Engine 29.3.0): when a verb a plugin names in `errorHooks` exits non-zero, its `prism-cli-plugin-hooks` reply is printed under What's next; `PRISM_CODE_NO_HOOKS=1` turns them off. The first-party plugin `prism-doctor` ships as a second binary of the package: `prism-code doctor` checks Node.js, Docker, `./prismpm.lock` and the sigstore packages, and its hook suggests it when a Docker verb exits 64 or 69.
- `prism-code push <holo> <reference>` and `prism-code pull <reference> [<out.holo>]` (#292, `docs/proposals/292-push-pull-oci.md`, experimental): move a holo and its attestations to and from any OCI Distribution 1.1 registry, with a dependency-free client over `fetch`, or a local OCI image layout (`--store <dir>` or `dir://`), usable as the backing store of #349. The holo is one layer of a deterministic manifest (media type `application/vnd.uor.prism.holo.v1`, BLAKE3 in annotations beside the `sha256` digest, ADR-015), so one file has one digest on every registry. Each attestation line becomes an OCI 1.1 referrer with the same bytes, in cosign's layout; `--key` or `--keyless` also signs a statement per predicate that names the manifest, so `cosign verify-attestation` passes on the pushed reference and `oras discover` lists them. A registry without the referrers API uses the spec's tag schema. `pull` writes nothing until the digests, the archive, the BLAKE3 annotations, the verdict of `check` under `--policy`, every statement subject and an optional signer policy (the flags of `verify-attestation`) have passed. `registry/repo@blake3:<fingerprint>` addresses a holo by its fingerprint through a `blake3-<fingerprint>` tag and the bytes are verified. Credentials come from Docker's config, or `GHCR_TOKEN` or `GITHUB_TOKEN` for `ghcr.io`. New typed errors: `RegistryError`, `RegistryAuthError`, `ReferrersUnsupportedError`, `ManifestNotFoundError`, `DigestMismatchError`, `PullVerificationError`, `ReferenceInvalidError`. `@prism-code/spec` gains `OCI`.
- Provider services in `prism.toml` (#294, `docs/proposals/294-provider-services.md`, experimental), after Docker Compose's: a table under `[capabilities]` declares `provider = { type, options }`, and `prism-code providers up|down [<dir>] [--target browser|node] [--json]` or `resolveProviders` and `releaseProviders` in `prism-code/node` run `prism-provider-<type>` from the PATH with the options as flags, and produce the `setenv` key/values of its JSON Lines reply as `<NAME>_<VAR>`. Deny by default holds twice: `prism/capabilities/1` gains the kind `providers` (`allow-providers`, `deny-providers`), checked for every declaration before any provider starts, and a returned variable is produced only when the `variables` kind allows it, otherwise it is withheld and reported by name. Failures are `CapabilityDeniedError` (`capabilities.providers`), `ProviderNotFoundError`, `ProviderReplyError` and `ProviderFailedError`, and none quotes a reply line. `prism-provider-kv`, a local key-value store kept as one JSON file, ships as a package binary and is the reference provider. `@prism-code/verify` accepts the new set members. The plugin scan now skips names starting with `provider-`. Nothing inside a holo can read these variables yet, because the guest world imports nothing and `prism-code run` does not read `prism.toml`.
- `prism-code export <name@sha256:digest> [--out <dir> | --tar <file>]` (#290, experimental): writes the six-file browser export of a release verified in `.prism/oci`, or one deterministic ustar tarball of it, with the holo's attestation bundles copied byte for byte to `<name>.attestations.jsonl` beside the output (buildx's `local` and `tar` exporters); every file is read from its stored release blob, checked against its layer and its build manifest row, written and read back, and a difference is the new `ExportMismatchError` (`export_mismatch`, exit 2) with the export removed; `--json` prints the `prismpm/browser-export/1` receipt. `experimental_exportBrowser` and `experimental_checkExport` in `prism-code/node`. The shared Action's Pages closure check (`action/pages-closure.mjs`) now reads the release and checks the exported directory through the same module, so it also requires the exact six-file profile, and its container mounts the Action's checkout read-only instead of only `action/`.
- Runtime middleware in `prism-code` (#295, experimental, guide `docs/site/guides/write-a-middleware.md`): `Application.experimental_middleware` is a stack of named, tagged middleware over the four steps the runtime performs, `verify`, `instantiate`, `dispatch` and `record`, ordered by step, by `priority` and by `addRelativeTo` before or after a named middleware, with `remove`, `removeByTag`, `override`, `clone` and `use(pluggable)` after the AWS SDK for JavaScript v3 stack. Each step wraps one operation of its own, so `instantiate` is where a capability check can link imports. A middleware that throws anything but a `PrismError` raises the new `MiddlewareError` (`middleware_failed`); stack misuse fails with `middleware.step`, `middleware.name`, `middleware.relative` or `middleware.shape`. Tracing ships as the first middleware: `experimental_tracing({ tracer })` opens one OpenTelemetry span per step, `prism.<step>`, from a tracer the caller passes, so the package still has no dependencies. `runGuest` is unchanged.

### Breaking Changes
- `prism-code run` gates on `check` (#282, `docs/proposals/282-run-gated-on-check.md`, experimental, breaking): the holo is judged against the policy (`--policy`, default P2) with the capability set it will run under before it is instantiated. A failing verdict refuses with exit 1 and prints the verdict; no verdict refuses with exit 2. `--allow-unverified` runs it anyway with a warning on every start and is never the default. Every holo is P0 today, so `run` without a policy that accepts P0 or the flag now refuses. A policy's new `effects` member lists the impure effects the world may import; `[]` is the pure-world policy, reported as `policy.effects`.
- A guest that declares an import now fails to load with `CapabilityDeniedError` (`capability_denied`, check `capabilities.import`) instead of `PrismCodeError` `core.imports` (#279); the `prism-code` exit code stays 2.
- `prism-code inspect` on a `.holo` prints the human inspection instead of the 0.2.0 JSON summary, and `--json` prints `prismpm/holo-inspection/1`. A closure directory keeps the 0.2.0 summary.
- `prism-code check <holo>` judges the holo and returns a verdict instead of running `prismpm check` in the SDK image; the Docker-backed check is now `prism-code build --check` (#270).

### Bugs Fixed
- `prism-code attest --key` writes an empty DSSE `keyid`, so `cosign verify-blob-attestation` accepts the bundle (#292): cosign skips a signature whose `keyid` is not its own, and the key's hash there made such a bundle verify nowhere but in `prism-code`. The hash stays in `verificationMaterial.publicKey.hint`, and bundles already written still verify in `prism-code`.
- Keyless `prism-code attest` no longer fails intermittently with `(409) an equivalent entry already exists` from the public Rekor log. It waits 30 s for each Sigstore service instead of 5 s, so a slow answer is not re-sent, and when a re-sent entry is still refused as a duplicate it signs once more. The unused first entry stays in the log.

### Other Changes
- `prism-code check` without a holo, the 0.2.0 spelling of `build --check` (#270). It still runs `prismpm check` in the SDK image and prints a warning; it is removed in 0.4.0. Migration: replace `prism-code check [args]` with `prism-code build --check [args]`.

## [0.2.0] - 2026-10-23

### Features Added
- `load` opens a holo from bytes, a `Blob`, a path or a URL, and checks its digest footer and every section label.

- `acceptance` replays every example the holo carries and reports how many passed.
- `prism-code run` serves a holo, `prism-code vectors` replays its examples, and `prism-code inspect` prints what it says about itself.
- `prism-code check` and `prism-code build` run the build inside the toolchain image pinned by `prismpm.lock`. Docker is required.
